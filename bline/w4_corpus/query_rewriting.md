# 查询改写

查询改写在检索之前动手，把用户的原始问句变成更适合匹配的形式。最常见的一类是同义扩展：用户用"卡住""不动""没反应"描述同一个现象，文档里写的是"请求超时"，两边字面不重合，稀疏检索直接落空，改写把它们对齐到同一组词上。另一类是补全省略，句式里的代词和省略成分在脱离对话上下文后失去所指，补全之后才能与文档匹配。

多查询改写走得更远，一次生成多个不同角度的查询，分别检索后合并结果。理由是单一表述会锁定在语义空间的一个方向上，而答案可能分布在几个不同的表述附近。这一路的代价是检索次数成倍增加，延迟叠加，合并去重也需要额外策略，否则同一份文档会以多个身份挤占前若干名，把真正不同的候选挤出去。

改写最大的风险是引入错误前提。模型在补全省略时会把猜测当成事实写进查询，于是检索朝一个文档里根本不存在的方向跑，答案被系统性地推向错误的那一侧。这类失效比"没有命中"更隐蔽，因为检索照样返回了看起来相关的结果，只是全部无关。对策是让改写保持保守：只在文档里确实存在对应表述时才扩展，遇到指代不明时保留原样并降低权重，而不是硬补。

改写的收益需要和它带来的噪声一起报告。评测时不能只跑改写后的查询，要同时跑原始查询作为对照，并按查询类型分层看——多跳查询和指代密集的对话查询通常从改写中获益最多，简单的单跳事实查询几乎没有收益，白白付出延迟代价。改写也会与重排产生交互：如果重排已经解决了大部分排序问题，改写带来的额外候选里质量会下降，需要在合并阶段控制数量，否则噪声候选会挤掉重排排好的结果。
